# Temporal Worker Scaling Simulator — Workflow Cache / Sticky Execution Build Order

## Objective

Add Workflow caching to the simulator in a way that clearly teaches the relationship between:

```text
Workflow cache
→ memory consumption
→ cache hits / misses
→ Workflow replay
→ Workflow Task CPU cost and latency
```

without cluttering the existing topology.

The current scene architecture should remain intact.

This pass should **not yet attempt to fully visualize Worker-specific Sticky Task Queues or sticky routing across multiple Workers**. Implement the cache/replay mechanics first in a single-Worker model. Sticky routing becomes a later multi-Worker milestone.

The key mental model is:

> A Worker may retain the reconstructed in-memory state of a Workflow Execution after a Workflow Task completes. A later Workflow Task can use that warm state instead of reconstructing it through replay.

The cache contains reconstructed Workflow execution state, not simply a stored copy of Event History.

This optimization applies to **Workflow Tasks only**, never Activity Tasks.

---

# 1. Preserve the current simulator topology

Do not redesign:

```text
Client
→ Temporal Service Core
→ Workflow / Activity Task Queues
→ Pollers
→ Slots
→ completion / command return
→ Temporal Core
```

Keep:

- Temporal Service boundary
- Worker boundary
- Workflow Task lane
- Activity Task lane
- middle completion-return lane
- existing Workflow/Task shape grammar
- green completed-Workflow state
- Triggered / Continuous workload modes
- current Task lifecycle correctness

Workflow cache should be added **inside the Worker** as another Worker subsystem.

# 5. Add explicit cache state to each Workflow Execution

The engine should track at least:

```ts
cachedWorkerId: string | null
lastCacheAccessAt: number | null
```

For the single-Worker implementation this may seem redundant, but preserve the Worker ID now so the model can support multiple Workers later.

A Workflow may be:

```text
COLD
```

or:

```text
WARM on Worker A
```

This state is separate from:

```text
Workflow Task currently executing
```

A Workflow may remain cached while it is waiting for an Activity, Timer, etc. and consume **no Workflow Task Slot**.

That distinction is essential.

---

# 6. Add Worker cache entries

Recommended engine structure:

```ts
WorkflowCacheEntry {
  workflowId
  workerId
  insertedAt
  lastUsedAt
  memoryMb
}
```

The Worker should maintain a collection of cache entries.

Use **LRU eviction**.

On every cache hit or successful Workflow Task completion, refresh:

```text
lastUsedAt
```

# 7. Add Workflow Cache Capacity control

Expose a Worker control:

```text
Workflow Cache Capacity
[ slider / numeric input ]  4
```

Suggested educational range:

```text
0 – 50
```

Start with a small default that makes cache behavior observable, perhaps:

```text
4
```

or:

```text

```

This is intentionally pedagogical.

The control represents:

> Maximum number of Workflow Executions this simulated Worker can retain warm.

---

# 8. Support Cache Capacity = 0

Allow:

```text
Workflow Cache Capacity = 0
```

This should be a useful teaching scenario.

Expected:

```text
every later Workflow Task
→ cache miss
→ replay
```

Initial Workflow Tasks are naturally cold regardless.

This gives the user an easy way to observe the cost of having no cache.

---

# 9. Insert/refresh cache after Workflow Task completion

When a Workflow Task successfully completes and the Workflow remains open:

```text
Workflow Task finishes
→ cache Workflow state
```

If the Workflow is already cached:

```text
refresh existing cache entry
```

If not:

```text
insert new cache entry
```

If capacity would be exceeded:

```text
evict LRU entry first
```

Then insert the new Workflow.

---

# 10. Remove cache state when Workflow completes

When the final Workflow Task completes the Workflow Execution:

```text
Workflow → COMPLETED
```

remove its cache entry.

Then preserve the existing:

```text
○ → green ✓ → hold → fade
```

completion behavior.

Completed Workflows should not continue consuming simulated cache memory.

---

# 11. Add LRU eviction behavior

When:

```text
cache size > configured capacity
```

evict the least recently used Workflow entry.

Example:

```text
Capacity = 3

Cache:
[W1] [W2] [W3]

W2 accessed

Order effectively becomes:
W1 oldest
W3
W2 newest

Insert W4

Evict:
W1

Cache:
[W3] [W2] [W4]
```

Emit a semantic event:

```text
CACHE_EVICTED
```

with:

```text
workflowId
workerId
reason
```

Initial reason:

```text
CAPACITY
```

Later:

```text
MEMORY_PRESSURE
WORKER_REMOVED
```

may be added.

---

# 12. Make eviction visually subtle but observable

When a cache entry is evicted:

```text
[W1]
```

briefly indicate eviction and remove it.

Possible treatment:

```text
[W1] → fade
```

with a tiny:

```text
evicted
```

label if helpful.

Do not animate the Workflow circle itself moving out of the Worker.

The persistent Workflow still exists in Temporal.

Only its warm Worker state was lost.

---

# 13. Add cache-hit detection before Workflow Task execution

When a Workflow Task is assigned to a Workflow Slot:

Check:

```text
Does this Worker have a valid cache entry for this Workflow?
```

If yes:

```text
CACHE HIT
```

If no:

```text
CACHE MISS
```

Do this only for Workflow Tasks.

Activity Tasks completely ignore the Workflow cache.

---

# 14. Cache-hit behavior

On a hit:

```text
Workflow Task reaches Workflow Slot
→ cached state found
→ execute only the new Workflow work
```

No replay phase.

The cache entry should briefly highlight:

```text
Workflow Cache

[W1] [W2] [W7]
           ↑
          hit
```

Keep the visual effect restrained.

Suggested:

- slightly brighter outline;
- brief pulse;
- optional tiny `hit` indicator.

Do not add another moving object.

---

# 15. Cache-miss behavior

On a miss:

```text
Workflow Task reaches Workflow Slot
→ no cached state
→ replay required
→ normal Workflow decision execution
```

The Workflow Task remains in the same Workflow Slot.

Do not create a Replay Task.

Use an execution sub-state:

```text
RUNNING_REPLAY
→ RUNNING_DECISION
```

---

# 16. Make replay visually obvious

A miss should be easy to perceive.

Suggested:

```text
Workflow Slot

[ ■ ↻ ]

REPLAY
```

or:

```text
[■]

Replay ▰▰▰▱
```

Keep it localized to the Workflow Slot.

After replay completes:

```text
REPLAY indicator disappears
→ normal Workflow execution continues
```

The same blue Workflow Task square remains present throughout.

---

# 17. Replay must consume CPU

Replay should use the Worker's shared CPU resource.

That is essential to the teaching model.

Conceptually:

```text
cache miss
→ replay CPU work
→ Workflow Slot occupied longer
→ shared CPU utilization rises
```

A cache hit avoids that replay work.

Do not model replay as merely an arbitrary visual delay.

---

# 18. Use Event History size to determine replay cost

Each Workflow already has or should gain a normalized History size.

Replay work should scale with History.

Recommended simple model:

```text
replayCpuSeconds =
historyUnits × replayCpuPerHistoryUnit
```

Do not attempt to predict actual Temporal replay latency.

The values are normalized educational constants.

Centralize:

```ts
replayCpuPerHistoryUnit
```

in the simulation constants.

---

# 19. Do not replay Activities

This is a hard semantic invariant.

During Workflow replay:

```text
completed Activities
```

must **not execute again**.

Do not:

- create new orange Activity Tasks;
- occupy Activity Slots;
- animate old Activities;
- issue external I/O.

Replay only reconstructs Workflow state using the recorded history/results.

---

# 20. Add normalized cache memory consumption

Each cached Workflow consumes Worker memory.

Use a simple initial model:

```text
cachedWorkflowMemoryMb = fixed normalized amount
```

Example:

```text
4 MB
```

or another centralized pedagogical value.

Then:

```text
cacheMemory =
cacheEntryCount × cachedWorkflowMemoryMb
```

Include this in Worker memory accounting.

---

# 21. Integrate cache with the existing Memory indicator

Worker memory should conceptually become:

```text
Memory Used =
base Worker memory
+ active Task memory
+ Workflow cache memory
```

At this stage, avoid introducing detailed GC/OOM behavior.

The important visible relationship is:

```text
cache capacity ↑
→ cached Workflows ↑
→ memory use ↑
```

---

# 22. Make cache capacity and physical memory separate concepts

Do not make:

```text
Cache Capacity
```

and:

```text
Memory
```

the same control.

They represent different constraints.

Example:

```text
Cache Capacity = 20 workflows
Memory Capacity = 1 GiB
```

The cache says how much state the Worker *wants* to retain.

Memory says how much physical capacity exists.

This distinction will later support:

```text
large configured cache
+
low memory
→ memory pressure
→ forced cache eviction
```

---

# 23. Add memory-pressure eviction only after basic cache behavior works

Implement in two stages.

### Stage A

Cache limited only by:

```text
Workflow Cache Capacity
```

Verify:

- hit
- miss
- eviction
- replay
- CPU interaction

### Stage B

Then integrate physical memory pressure.

If:

```text
memoryUsed > memoryCapacity
```

evict LRU cache entries until:

```text
memoryUsed <= memoryCapacity
```

where possible.

Emit:

```text
CACHE_EVICTED
reason = MEMORY_PRESSURE
```

Do not crash the Worker yet.

---

# 24. Do not make high memory arbitrarily slow execution

Do not implement:

```text
90% memory
→ everything slows by X%
```

That is too speculative for this teaching model.

For now, memory affects performance primarily through:

```text
memory pressure
→ cache eviction
→ cache miss
→ replay
→ CPU
```

This is clean and explainable.

# 33. Ensure Workflow Slots and cache remain separate

This is a critical educational invariant.

Example:

```text
Workflow Cache

[W1] [W2] [W3] [W4]

Workflow Slots

[ ] [ ]
```

This is completely valid.

Those Workflows are warm but currently waiting.

A cached Workflow does not continuously consume a Workflow Task Slot.

Likewise:

```text
Cache size = 20
Workflow Slots = 2
```

does not mean 20 Workflow Tasks may execute concurrently.

# 39. Add strict cache invariants

The engine should enforce:

### One cache location per Workflow

For current model:

```text
Workflow has ≤ 1 cachedWorkerId
```

### Completed Workflow has no cache entry

```text

```

### Activity Tasks never consult cache

### Cache miss does not re-run Activities

### Cache hit eliminates replay work

### Cache capacity never exceeds configured logical capacity

except transiently during atomic insertion/eviction operations if implementation requires it.

# 42. Live cache-capacity changes

Increasing:

```text
2 → 10
```

creates additional empty cache capacity.

It does **not** magically restore previously evicted Workflows.

Those Workflows remain cold until a future Workflow Task executes and warms them again.

Decreasing:

```text
10 → 3
```

must immediately evict LRU entries until:

```text
cacheSize <= 3
```

---

# 43. Live memory changes

After memory-pressure eviction is implemented:

Increasing memory:

- preserves currently cached entries;
- allows more future entries to remain;
- does not resurrect evicted state.

Decreasing memory:

- recompute pressure;
- evict LRU cache entries as needed.

Do not kill active Workflow Tasks solely because memory decreases in this milestone.

# 46. Success criterion

The cache milestone is complete when a user can discover this relationship interactively:

```text
small cache
→ more evictions
→ more cache misses
→ more replay
→ more Workflow CPU
→ slower Workflow Task processing
```

and:

```text
larger cache
→ more memory consumption
→ fewer replays
→ less Workflow CPU
```

while also understanding:

```text
cached Workflow
≠
actively executing Workflow Task
```

---

## Final implementation principle

The simulator should teach sticky execution in increasing layers of complexity:

```text
Layer 1
Workflow state can be warm on a Worker.

Layer 2
Warm state avoids replay.

Layer 3
Warm state costs memory.

Layer 4
Too little cache/memory causes eviction and replay.

Layer 5 — later
With multiple Workers, Temporal prefers the Worker with warm state.

Layer 6 — later
That preference expires when the warm Worker cannot start the Task promptly.
```

Do **not** try to teach all six layers at once.

The current phase should get Layers 1–4 working extremely clearly. Once those are trustworthy, multi-Worker sticky routing will be much easier to add without overwhelming the existing simulation.
