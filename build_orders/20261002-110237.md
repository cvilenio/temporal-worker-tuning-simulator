# Third-pass brief: human-readable time + explicit Temporal processing flow

## Goal

This pass should make the simulator readable at a normal `1x` presentation speed.

Do not solve readability primarily by requiring users to run the entire simulation at `0.05x`.

Instead:

- allow workloads to occur at human-readable rates;
- keep playback/time scaling as a separate concept;
- introduce an explicit Temporal Service processing node;
- ensure **Tasks only visually flow toward Workers**;
- represent Worker → Temporal traffic as completions/results, not Tasks flying backward.

---

## 1. Separate workload rate from playback speed

The current model effectively requires extremely low playback multipliers because rates such as:

```text
4 Workflow starts / second
```

are inherently impossible for a human to visually follow one-by-one.

### Change the Workflow Start Rate control

Replace the current single slider with:

```text
Workflow starts

[ 12 ] [ per minute ▼ ]
```

Supported units:

```text
per second
per minute
per hour
```

Keep the entered number primarily integer-based.

Examples:

```text
1 / second
30 / minute
12 / minute
1 / minute
10 / hour
```

Internally, normalize everything to workflows/second.

This gives us fine control **without making users manipulate decimals**.

For example:

```text
12 / minute = one Workflow every 5 seconds
6 / minute  = one Workflow every 10 seconds
1 / minute  = one Workflow every 60 seconds
```

### Recommended default

Use something like:

```text
12 / minute
```

rather than:

```text
1 / second
```

for the teaching/demo configuration.

At `1x`, that gives enough time to watch individual Workflow lifecycles.

---

## 2. Redefine the speed control as a time-scale control

The normal speed control should now adjust **presentation/simulation time**, not compensate for an excessively high workload rate.

Use a slider such as:

```text
Time scale

0.25x ───── 0.5x ───── 1x ───── 2x
                     ▲
```

Default:

```text
1x
```

At sensible workload rates, `1x` should be comfortably understandable.

### Add explicit fast-forward

Fast backlog draining is a different use case.

Provide separate controls such as:

```text
[4x] [8x]
```

or:

```text
Fast forward
```

Ideally this can be momentary/temporary.

Conceptually:

```text
normal teaching:
0.25x – 2x

operational fast-forward:
4x / 8x
```

Don't optimize the primary slider around queue-draining.

---

# 3. Introduce an explicit Temporal Service Core

The current Temporal box contains Workflow Executions and queues, but nothing visually explains **how an incoming event becomes a Task, or how a completion creates subsequent work**.

Add a central component inside the Temporal Service boundary.

Suggested label:

## Temporal Service Core

Subtitle:

```text
Workflow state · history · task scheduling
```

Do **not** call it “brain” in the UI.

Conceptually:

```text
┌──────────────────── TEMPORAL SERVICE ────────────────────┐
│                                                         │
│                ┌─────────────────────┐                  │
│                │ Temporal Service    │                  │
│                │ Core                │                  │
│                │                     │                  │
│                │ Workflow state      │                  │
│                │ History             │                  │
│                │ Task scheduling     │                  │
│                └──────────┬──────────┘                  │
│                           │                             │
│                  schedules Tasks                        │
│                           │                             │
│          ┌────────────────┴───────────────┐             │
│          ▼                                ▼             │
│   Workflow Task Queue             Activity Task Queue   │
│   ■ ■ ■                          ■ ■ ■ ■                 │
│                                                         │
└─────────────────────────────────────────────────────────┘
```

The queues can optionally be grouped/labeled:

```text
Task Queues / Matching
```

This is an abstraction; it does not need to expose actual Temporal server microservices.

---

# 4. Put persistent Workflow Executions at the Service Core

Instead of having Workflow Execution circles feel like unrelated indicators floating above the queues, associate them spatially with the Temporal Service Core.

For example:

```text
Temporal Service Core

Workflow Executions

○  ○  ○  ○
```

or inside/adjacent to the Core:

```text
┌──── Temporal Service Core ────┐
│                              │
│ Active Workflows             │
│ ○ ○ ○ ○ ○        +8         │
│                              │
│ State / History              │
└──────────────────────────────┘
```

A Workflow circle:

```text
○
```

appears when the Client start request is accepted.

It persists until that Workflow completes.

---

# 5. Make the Client → Temporal path explicit

At the configured rate:

```text
CLIENT

○
 \
  \ Workflow Start
   \
    ▼

TEMPORAL SERVICE CORE
```

When the request reaches the Core:

```text
request ○
     ↓

persistent Workflow ○
```

Then the Core schedules:

```text
blue Workflow Task ■
```

into:

```text
Workflow Task Queue
```

So visually:

```text
Client ○
   ↓
Service Core
   ├── Workflow ○ persists
   │
   └── blue ■ → Workflow Task Queue
```

This provides an understandable transformation location.

---

# 6. Critically: Tasks should not fly backward from Workers to queues

This is probably the most important correction.

When a Task reaches the Worker and finishes executing, **that Task is done**.

Do not animate the same Task square flying back into Temporal or back into a queue.

Instead:

```text
Workflow Queue
     ■
     ↓
Poller
     ↓
Workflow Slot
    [■]

    executes

    ■ completes/disappears here
```

Then send a visually different **completion/result signal** back to the Temporal Service Core.

For example:

```text
Worker Slot                    Temporal Core

 [■]
  │
  │ complete
  └ - - - - - - - - - - - - → ◇
```

The return signal should **not be a Task square**.

It could simply be:

- a temporary thin dashed arrow;
- a tiny neutral pulse;
- a very small diamond;
- a brief `Completed` signal.

It should disappear when the Core receives it.

---

# 7. Establish directional visual grammar

This should make the whole system much easier to parse.

### Work/Tasks travel:

```text
Temporal Core
     ↓
Task Queue
     ↓
Poller
     ↓
Slot
```

Primarily:

```text
LEFT → RIGHT
```

### Results/events travel:

```text
Worker Slot
     ↓
Temporal Service Core
```

Primarily:

```text
RIGHT → LEFT
```

But use a distinctly different visual treatment.

For example:

```text
Tasks:
solid colored squares

Completion/result:
thin neutral dashed pulse
```

So the user never mistakes return traffic for another Task.

---

# 8. The Temporal Core creates subsequent Tasks

For the default sequential Workflow:

```text
Client
  ○
  ↓

Temporal Core
  Workflow ○
  │
  └─ blue ■

Workflow Queue
  blue ■
     ↓

Worker Workflow Slot
  [blue ■]
     │
     │ Workflow Task completes with command:
     │ schedule Activity
     ▼

completion / commands
- - - - - - - - - - → Temporal Core
                         │
                         └─ orange ■
```

Then:

```text
Activity Queue
orange ■
   ↓

Worker Activity Slot
[orange ■]
   │
   │ Activity completes
   ▼

completion
- - - - - - - - - - → Temporal Core
                         │
                         └─ blue ■
```

Then repeat.

This is the actual causal rhythm the visual should teach:

```text
CORE
 ↓
WFT
 ↓
WORKER
 ↑
commands/completion
 ↑
CORE
 ↓
Activity
 ↓
WORKER
 ↑
completion
 ↑
CORE
 ↓
next WFT
```

This matches the standard Temporal abstraction: interactions/events create Tasks, the Service records the event and schedules work, Tasks wait in Task Queues, and Workers poll and execute them.

---

# 9. Avoid implying that Temporal executes Workflow logic

There is one semantic nuance here worth being careful about.

The new Core should **not appear to make the Workflow's application decisions itself**.

The Worker executes Workflow code.

So:

```text
Workflow Worker
[blue ■]
```

is where the Workflow determines:

```text
schedule Activity
start Timer
complete Workflow
...
```

Then the result/commands return to Temporal.

The Core:

- records durable state/history;
- applies the outcome;
- schedules resulting Tasks.

So avoid a label like:

```text
Decision Engine
```

for the Temporal Service.

Use:

```text
Temporal Service Core
Workflow state · history · task scheduling
```

instead.

---

# 10. Default Workflow pattern remains sequential

Keep the recently corrected default:

For three Activities:

```text
WFT
 ↓
Activity
 ↓
WFT
 ↓
Activity
 ↓
WFT
 ↓
Activity
 ↓
final WFT
```

This gives:

```text
4 Workflow Tasks
3 Activity Tasks
```

and makes the back-and-forth orchestration pattern much clearer than fan-out.

Eventually we can expose:

```text
Workflow pattern:
Sequential
Fan-out
```

but not yet.

---

# 11. Revisit transit timing after lowering workload rates

Once the default is something like:

```text
12 Workflows / minute
```

rather than:

```text
4 Workflows / second
```

we should no longer need absurdly slow global playback just to see dispatch.

At `1x`, target roughly:

```text
Client → Core        500–800 ms

Core → queue         300–500 ms

Queue → Poller       400–600 ms

Poller claim         250–400 ms

Poller → Slot        400–600 ms

Completion → Core    400–600 ms
```

These are **presentation timings**, not claims about Temporal network latency.

The renderer is intentionally slowing movement enough for a human to perceive causality.

---

# 12. Don't show everything at high-speed mode

At:

```text
4x / 8x
```

it is okay to simplify motion.

Fast-forward exists to change system state, not to teach individual Task movement.

At normal speeds:

```text
0.5x – 1x
```

preserve full transitions.

At fast-forward:

- shorten transit;
- sample repetitive events;
- keep queue depths/metrics accurate.
