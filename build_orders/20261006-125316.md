# Temporal Worker Scaling Simulator — Worker Identity, Cache Memory, Replay UI Cleanup

## Goal

Refine the current sticky-cache implementation without changing the overall topology or engine model.

This pass should address:

- Worker identity labeling;
- redundant affinity badges;
- cache color semantics;
- replay-label overlap;
- memory accounting when cache entries are removed;
- deterministic validation that cache replacement remains LRU;
- visual placement of cache relative to Workflow execution.

Do not redesign the scene or add new features in this pass.

---

## 1. Establish Worker identity at the Worker container level

Replace the current ambiguous/floating Worker identity presentation with an explicit Worker heading.

Preferred:

```text
WORKERS (1)

┌──────────────────────────┐
│ WORKER A                 │
│                          │
│ ...                      │
└──────────────────────────┘
```

For multiple Workers later:

```text
WORKERS (2)

┌──────────────┐  ┌──────────────┐
│ WORKER A     │  │ WORKER B     │
│ ...          │  │ ...          │
└──────────────┘  └──────────────┘
```

The Worker letter belongs in the Worker title.

---

## 2. Remove redundant Worker-letter badges inside the same Worker

Inside Worker A, do not repeatedly label:

```text
A
A
A
```

on cache entries or other components when the enclosing container already says `WORKER A`.

For example, prefer:

```text
Workflow Cache
[WF1] [WF3] [WF7]
```

not:

```text
[A:WF1] [A:WF3] [A:WF7]
```

Worker identity is already established by the containing Worker card.

---

## 3. Keep affinity badges only where they convey routing information

An Active Workflow badge such as:

```text
○ᴬ
```

is useful only because it means:

> this Workflow is currently warm on Worker A.

Keep this information only where it adds meaning.

Recommended rule:

- **single Worker visible:** hide affinity badge by default;
- **multiple Workers visible:** show `A`, `B`, etc. on warm Workflow indicators.

This avoids visual noise when the badge carries no useful distinction.

---

## 4. Rename cache display items clearly

Use concise Workflow identities inside the cache:

```text
Workflow Cache

[WF1] [WF4] [WF9] [ ]
3 / 4
```

Do not repeat the Worker ID inside each cell.

Keep stable Workflow IDs so cache hits/evictions remain trackable.

---

## 5. Change normal cache-entry color away from green

Green is already being used to mean:

```text
Workflow completed successfully
```

Do not use the same strong green as the normal resting state of cached Workflows.

Preferred cache states:

### Normal cached

Neutral/cool tone.

### Cache hit

Brief highlight/pulse.

### Eviction

Brief fade or warning accent.

### Completion

Green remains reserved for:

```text
Workflow ○ → ✓
```

This keeps color semantics clean.

---

## 6. Make cache-hit highlighting transient

When a cache hit occurs:

```text
[WF7]
```

may briefly brighten/pulse for a short duration.

Do not leave it permanently in a special success color.

Suggested real-time highlight:

```text
300–600 ms
```

Then return to the normal cache-cell appearance.

---

## 7. Fix replay-label overlap

Current problem:

Adjacent Workflow Slots can both show:

```text
REPLAY
```

and the labels overlap visually.

Do not use free-floating repeated text underneath each adjacent Slot.

Preferred per-Slot treatment:

```text
[■ ↻] [■ ↻]
```

or:

```text
[■] [■]
 ↻   ↻
```

with the replay indicator bound to each Slot.

Alternative if text is desired:

```text
Workflow Slots
[■] [■]

2 replaying
```

but avoid:

```text
REPLAYREPLAY
```

---

## 8. Replay indicator must derive from engine state

A replay glyph may appear only while:

```text
task.state === RUNNING_REPLAY
```

When the engine transitions to normal Workflow execution:

```text
RUNNING_DECISION
```

the replay indicator must disappear immediately.

No independent animation timer should keep it visible.

---

## 9. Validate cache memory contribution explicitly

Worker memory should be:

```text
memoryUsed =
baseWorkerMemory
+ activeTaskMemory
+ workflowCacheMemory
```

where:

```text
workflowCacheMemory =
cacheEntryCount × cachedWorkflowMemory
```

If cache entries disappear, memory usage must fall accordingly.

---

## 10. Add deterministic memory-release test

Create a test like:

```text
baseWorkerMemory = B
cachedWorkflowMemory = M

cache entries = 4
active tasks = 0
```

Expected:

```text
memoryUsed = B + 4M
```

Then remove all four cache entries.

Expected:

```text
memoryUsed = B
```

Assert the exact delta:

```text
memoryBefore - memoryAfter = 4M
```

---

## 11. Add active-task memory separation test

Configuration:

```text
cache entries = 0
active tasks = 2
```

Expected:

```text
memoryUsed =
baseWorkerMemory
+ memory for active Task 1
+ memory for active Task 2
```

Memory must not fall to zero simply because the cache becomes empty.

This verifies:

```text
cache memory != total Worker memory
```

---

## 12. Add completion-driven cache memory test

Scenario:

```text
WF1 cached
WF1 final Workflow Task completes
```

Expected:

```text
WF1 cache entry removed
→ memory drops by one cachedWorkflowMemory unit
```

The existing green-completion visual hold may remain for ~2 seconds, but engine memory/cache state should already reflect completion.

---

## 13. Add eviction-driven memory test

Scenario:

```text
cache full
insert new Workflow
LRU entry evicted
```

Expected:

```text
old entry memory removed
new entry memory added
```

If all cache entries have equal fixed memory cost, total memory should remain unchanged.

Example:

```text
4 entries before
4 entries after

cache memory contribution remains 4M
```

This catches double-counting during replacement.

---

## 14. Add cache resize-down memory test

Start:

```text
Cache Capacity = 5
cache size = 5
```

Reduce:

```text
5 → 2
```

Expected:

- 3 LRU entries evicted;
- cache memory decreases by exactly `3M`;
- two most-recently-used entries remain.

---

## 15. Verify memory-pressure eviction updates memory immediately

If memory-pressure eviction is implemented:

```text
memoryUsed > memoryCapacity
→ evict LRU cache entry
```

After each eviction:

```text
memoryUsed
```

must be recomputed immediately.

Do not wait for a later render cycle or unrelated event.

---

## 16. Add visual memory test

Manual scenario:

1. Fill cache to capacity.
2. Observe memory bar.
3. Complete/evict all cached Workflows.
4. Observe memory bar again.

Expected:

```text
memory decreases
```

but stays above zero because of:

```text
base Worker memory
```

and any active Tasks.

---

## 17. Revalidate true LRU ordering

Add/retain a deterministic test:

```text
capacity = 3

W1 inserted
W2 inserted
W3 inserted

W1 cache hit
W2 cache hit

insert W4
```

Expected oldest entry:

```text
W3
```

Therefore:

```text
W3 evicted
```

This verifies that `lastUsedAt` is refreshed on hits.

---

## 18. Verify replay rewarming updates LRU

Scenario:

```text
W1 evicted
later W1 misses
W1 replays
W1 WFT succeeds
```

Expected:

```text
W1 reinserted
W1 becomes most recently used
```

It should not immediately be a candidate for eviction simply because its Workflow ID is old.

---

## 19. Verify completion removes cache entry regardless of recency

Even if a completed Workflow is the most recently used:

```text
WF1 completes
```

Expected:

```text
WF1 removed from cache immediately
```

LRU recency does not preserve completed Workflows.

---

## 20. Keep Workflow Cache visually associated with Workflow execution

Place the cache physically nearer:

```text
Workflow Pollers
Workflow Slots
```

than:

```text
Activity Pollers
Activity Slots
```

The layout should reinforce:

> Workflow cache applies only to Workflow Tasks.

Do not place the cache where it visually appears shared equally by Workflow and Activity execution.

---

## 21. Preserve Activity independence from cache

Add a regression test:

Changing:

```text
Workflow Cache Capacity
```

must not directly alter:

- Activity cache state;
- Activity replay behavior;
- Activity Task execution semantics.

There is no Activity cache/replay equivalent in this model.

# Acceptance criteria

This pass is complete when:

- Worker identity is established once at the Worker container.
- Redundant `A` labels are gone.
- Affinity badges only appear when they convey useful routing information.
- Cache cells no longer use completion-green as their default color.
- Replay indicators never overlap.
- Memory falls when cache entries are removed.
- Memory never incorrectly falls to zero merely because cache is empty.
- Cache replacement does not double-count memory.
- LRU remains deterministic.
- Cache entries compact without visual gaps.
- Workflow Cache is visually associated with Workflow execution, not Activity execution.

That would be my cleanup pass before adding more behavior.
