## Temporal Worker Scaling Simulator — Multi-Worker Sticky Affinity + RPC Semantics Build Order

### Goal

Extend the existing simulator so it teaches:

- Workers initiate polling to Temporal.
- Temporal returns Tasks on those polls.
- Workers send Workflow commands / Activity results back to Temporal through outbound RPCs.
- Workflow cache is Worker-local.
- Subsequent Workflow Tasks prefer the Worker that has warm state.
- That preference is soft, not permanent.
- If the warm Worker cannot start the Task within the sticky timeout, the Task falls back to the shared Workflow Task Queue and may be processed elsewhere with replay.

Do not redesign the existing lane topology.

Current Temporal docs describe Pollers as long-polling connections initiated by Workers, with the received Task delivered into an execution slot. Workflow Tasks generate Commands that Workers send back to Temporal, and Activities similarly report their result. :chatgpt-content-reference{index="0"}

---

## 1. Rename the completion rail

Change the current generic label:

```text
COMMAND / COMPLETION RETURN
```

to something clearer, such as:

```text
COMMANDS / RESULTS → TEMPORAL
```

or:

```text
WORKER → TEMPORAL RPC
```

I prefer the first for the main UI and the second as explanatory/help text.

The rail represents:

```text
Workflow Task:
Worker → Commands → Temporal

Activity Task:
Worker → result/failure → Temporal
```

Do not imply that the Task itself returns.

---

## 2. Keep Task flow visually left-to-right

Preserve:

```text
Temporal Queue → Poller → Slot
```

as the visible Task path.

Do not reverse the primary work lanes.

The fact that the Worker initiated the long poll should be represented separately and subtly.

---

## 3. Add a lightweight Poll request visual state

Each Poller should have a semantic state like:

```text
IDLE
LONG_POLLING
TASK_RECEIVED
DISPATCHING
```

While long-polling, optionally show a faint outbound request indication:

```text
Queue  · · · · ← ○ Poller
```

When a Task is matched:

```text
Queue ■ ───────→ ○ Poller
```

This makes the directionality accurate:

```text
Worker asks for work →
Task comes back ← on the existing request
```

Do not draw permanent two-way arrows everywhere.

The poll-request indication should be low contrast and secondary.

---

## 4. Poll visualization must remain optional in dense scenes

When Poller count becomes large, rendering every long-poll pulse will become noisy.

Implement a display rule such as:

- show individual poll-request animation at low Poller counts;
- suppress or aggregate it above a visual threshold.

Do not let this feature interfere with the main Task motion.

---

# Multi-Worker foundation

## 5. Add multiple Worker instances

Support:

```text
Worker count = 1..N
```

Each Worker must have independent:

- Workflow Pollers
- Workflow Slots
- Activity Pollers
- Activity Slots
- CPU
- memory
- Workflow cache

For example:

```text
Worker A
Worker B
Worker C
```

Workers poll the same shared Task Queues.

Do not share cache state between them.

---

## 6. Give Workers stable display IDs

Use:

```text
A
B
C
```

or:

```text
W1
W2
W3
```

I recommend:

```text
Worker A
Worker B
```

because Workflow IDs already use `W1`, `W2`, etc.

Cache cells can then show:

```text
WF1
WF7
```

while Worker identity remains `A`, `B`.

---

## 7. Preserve existing deterministic routing for non-sticky work

For:

- initial Workflow Tasks;
- Activity Tasks;
- Workflow Tasks with no valid sticky affinity;

use deterministic round-robin across eligible Workers.

Eligibility still requires:

```text
appropriate Poller available
AND
appropriate Slot capacity available
AND
Worker active
```

No randomness unless intentionally seeded.

---

# Sticky affinity engine

## 8. Treat cache location as sticky affinity

When a Workflow Task successfully executes on Worker A and leaves the Workflow open:

```text
cache Workflow state on A
```

and set:

```text
workflow.cachedWorkerId = A
```

That Worker is now the preferred destination for the next Workflow Task.

This means:

```text
cache location
=
warm-state affinity
```

not durable ownership.

---

## 9. Add Workflow Task routing state

A Workflow Task should support something like:

```text
SHARED_QUEUE
STICKY_WAIT
SHARED_FALLBACK
```

A later Workflow Task for a warm Workflow should initially enter:

```text
STICKY_WAIT
preferredWorkerId = cachedWorkerId
```

rather than immediately being offered to every Worker.

---

## 10. Do not add a permanent visible sticky queue box

Keep the current UI clean.

Do not add:

```text
Sticky Queue A
Sticky Queue B
Sticky Queue C
```

as permanent additional lanes.

Instead, model the behavior in-engine and visualize affinity transiently.

---

## 11. Add a small warm-affinity badge

For a Workflow cached on Worker A, optionally show:

```text
WF1  A
```

or a tiny badge:

```text
○ᴬ
```

in the Active Workflows area.

The meaning is:

> Worker A currently has warm state for this Workflow.

Do not draw a permanent line between every Workflow and Worker.

---

## 12. Preferred Worker gets first opportunity

When a new Workflow Task is scheduled for a warm Workflow:

```text
preferredWorkerId = A
```

Only Worker A should initially be eligible to receive that Workflow Task.

If Worker A:

- has Workflow polling capacity;
- has Workflow Slot capacity;

it should acquire the Task normally.

Expected:

```text
sticky WFT
→ Worker A
→ CACHE_HIT
→ no replay
```

---

## 13. Sticky waiting must be visible but restrained

If Worker A cannot currently start the Workflow Task:

```text
Worker A busy
```

the Task should enter a temporary:

```text
Waiting for warm Worker A
```

state.

Do not add a new lane.

Possible visualization:

```text
Workflow Task Queue area

■  A
```

with:

- small Worker badge;
- subtle clock/progress ring;
- tooltip: `Waiting for warm Worker A`.

The Task should not look like normal shared-queue work while affinity is active.

---

## 14. Add sticky Schedule-to-Start timeout

Use a centralized simulated value:

```text
stickyScheduleToStartTimeout
```

Use the documented default behavior as the conceptual reference; keep the simulator value configurable internally rather than presenting it as a production-performance constant.

When the timeout expires:

```text
clear sticky preference
→ task enters normal shared Workflow Task Queue
```

Do not destroy/recreate the Task.

Its ID persists.

---

## 15. On sticky fallback, clear warm affinity for routing

When sticky fallback occurs:

```text
workflow.cachedWorkerId
```

should no longer guarantee routing to the previous Worker.

The old Worker may still physically contain an old cache entry until it is evicted, depending on how you choose to simplify the engine, but for v0 sticky routing I recommend:

```text
clear the authoritative warm affinity on fallback
```

to avoid ambiguous multiple warm owners.

Maintain the invariant:

```text
one Workflow
≤ one authoritative cachedWorkerId
```

---

## 16. Shared fallback allows another Worker to acquire the Task

Example:

```text
WF1 warm on A

A saturated
B idle

sticky timer expires

WF1 WFT
→ shared Workflow Task Queue
→ Worker B Poller
→ Worker B Slot
```

Since B does not have WF1 cached:

```text
CACHE_MISS
→ REPLAY
```

After successful execution:

```text
WF1 cached on B
workflow.cachedWorkerId = B
```

B becomes the new warm destination.

---

## 17. Visually show affinity transfer

When this happens:

```text
WF1 warm: A
```

becomes:

```text
WF1 warm: B
```

Update the small Worker badge.

Inside caches:

```text
Worker A cache:
[WF1] eventually removed / invalidated

Worker B cache:
[WF1] appears
```

Prefer making the transfer clear over preserving a more complex model of stale redundant cache state.

---

# Sticky timeout behavior

## 18. Test warm Worker temporarily busy

Scenario:

```text
WF1 cached on A
A has no free Workflow Slot
B idle
```

Schedule next WF1 Task.

Expected initially:

```text
Task waits for A
B does not immediately take it
```

If A frees a Slot before timeout:

```text
A acquires Task
→ cache hit
```

This teaches the locality preference.

---

## 19. Test sticky fallback

Same setup, but keep A blocked beyond timeout.

Expected:

```text
sticky wait expires
→ shared queue
→ B acquires
→ cache miss
→ replay
→ B becomes warm owner
```

This is the core sticky-routing scenario.

---

## 20. Make sticky timeout a hidden/advanced constant first

Do not immediately expose a UI slider.

The simulator is already complex.

Initially:

```text
sticky timeout = centralized simulation constant
```

Once behavior is validated, an advanced teaching control can be added later:

```text
Sticky fallback timeout
```

That would let the user explore:

```text
longer timeout
→ more locality
→ potentially more waiting

shorter timeout
→ faster failover
→ more replay
```

But defer that UI until the feature reads clearly.

---

# Cache + sticky interactions

## 21. Cache eviction removes affinity

If WF1 is cached on A and its cache entry is evicted:

```text
workflow.cachedWorkerId = null
```

The next WFT should use the shared Workflow Task Queue directly.

Expected:

```text
no sticky wait
→ any eligible Worker
→ replay
```

This is important.

Affinity cannot outlive the warm state it represents.

---

## 22. Workflow completion removes affinity

When the Workflow completes:

```text
remove cache entry
cachedWorkerId = null
```

existing green-check/fade behavior remains unchanged.

---

## 23. Worker removal invalidates its affinities

When Worker A drains/removes:

For every Workflow whose:

```text
cachedWorkerId === A
```

clear affinity.

Next Workflow Task:

```text
shared queue
→ eligible Worker
→ replay
```

Do not leave Workflows pinned to nonexistent Workers.

---

# RPC semantics

## 24. Workflow completion rail should originate from Workflow Slots

When a Workflow Task finishes:

```text
Workflow Slot
→ Commands / completion RPC
→ Temporal Core
```

Only when the Core receives/processes this response should it:

- persist resulting state;
- schedule Activities;
- complete Workflow;
- etc.

The Task itself ends at the Worker.

---

## 25. Activity completion rail should originate from Activity Slots

When an Activity finishes:

```text
Activity Slot
→ result RPC
→ Temporal Core
```

The Core then records the result and may schedule the next Workflow Task.

Do not visually imply that the Activity directly schedules the Workflow Task.

---

## 26. Rename diagnostics/events accordingly

Prefer engine events such as:

```text
WORKFLOW_TASK_RESPONSE_SENT
ACTIVITY_TASK_RESPONSE_SENT
```

or:

```text
RESPOND_WORKFLOW_TASK_COMPLETED
RESPOND_ACTIVITY_TASK_COMPLETED
```

over generic:

```text
RETURN
```

if the current engine names are vague.

No need to expose exact gRPC method names prominently in the UI.

---

# Renderer rules

## 27. Maintain one authoritative Task object

Sticky waiting, fallback, polling, replay, and execution must all operate on the same stable Task ID.

The Task must not be visually recreated during:

```text
sticky wait
→ fallback
→ shared queue
```

---

## 28. Add only transient affinity visualization

Allowed:

```text
■ᴬ
```

small badge.

Allowed:

```text
waiting for A
```

temporary status.

Avoid:

- permanent Worker affinity lines;
- permanent sticky lanes;
- additional background plumbing.

---

## 29. Keep replay visualization unchanged

On fallback to another Worker:

```text
Workflow Slot [■ ↻]
REPLAY
```

Use the existing replay treatment.

This connects sticky routing naturally to the cache feature the user already understands.

## 37. Polling remains mandatory

Even sticky Tasks must require Pollers.

Scenario:

```text
WF1 warm on A
A Workflow Pollers = 0
B idle
```

Before sticky timeout:

```text
A cannot receive Task
```

After timeout:

```text
shared routing may allow B
```

Warm cache must not bypass polling semantics. Temporal Pollers are the mechanism by which Workers receive Tasks. :chatgpt-content-reference{index="1"}

```text
WF1 warm on A
A Workflow Slots = 0
```

```text

```

# Manual teaching scenarios

## 39. Warm locality scenario

Configuration:

```text
2 Workers
Cache Capacity > active Workflows
adequate slots
```

Trigger one Workflow.

Expected:

```text
initial WFT → A
WF becomes warm on A
Activity may run anywhere
next WFT → A
cache hit
```

The user should be able to see the same Workflow repeatedly prefer A.

---

## 40. Warm Worker overloaded scenario

Create enough Workflow work to saturate A.

Have WF1 warm on A.

Expected:

```text
WF1 waits for A
```

If A recovers quickly:

```text
A takes it
hit
```

This demonstrates why sticky routing exists.

---

## 41. Sticky fallback scenario

Keep A saturated longer.

Expected:

```text
wait
→ timeout
→ shared queue
→ B
→ replay
→ warm state moves to B
```

This should be the signature teaching scenario.

# Visual acceptance criteria

## 42. Default scene must still be readable

With two Workers, the user should still immediately understand:

```text
Temporal
→ Queue
→ Worker Poller
→ Worker Slot
```

Do not allow the multi-Worker view to turn into a network diagram.

---

## 43. Sticky state should be discoverable, not dominant

At a glance, the user can see:

```text
WF1 warm on A
```

but the primary visual hierarchy remains Tasks, Queues, Pollers, and Slots.

---

## 44. Fallback must be visually obvious

The sequence should read:

```text
WF1 → prefers A
      waits
      timeout
      shared queue
      B
      REPLAY
```

without needing diagnostics.

# Implementation order

Implement in this exact sequence:

1. Rename/reframe completion rail.
2. Add explicit Poller `LONG_POLLING` state.
3. Add subtle optional Worker→Temporal poll-request visualization.
4. Add multiple Worker engine model.
5. Add Worker count UI.
6. Add independent Worker caches.
7. Add `preferredWorkerId` / sticky routing state.
8. Implement sticky wait.
9. Implement timeout fallback to shared queue.
10. Implement replay on fallback Worker.
11. Transfer warm affinity after successful replay/execution.
12. Clear affinity on cache eviction.
13. Clear affinity on Worker removal.
14. Add automated tests.
15. Add small warm-Worker badges.
16. Add sticky-wait visualization.
17. Add fallback animation.
18. Run manual teaching scenarios.
19. Only then adjust visual polish.

The important product principle is:

> **Cache explains why locality is valuable; sticky routing explains how Temporal tries to preserve that locality without making the Worker the durable owner.**

That is the next logical concept to add now that the single-Worker cache behavior is tested and stable.
