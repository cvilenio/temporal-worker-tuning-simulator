## Temporal Worker Scaling Simulator — Next Pass Implementation Order

### Goal

Refine the current simulator so the flow is visually unambiguous before adding any more features or aesthetic polish.

This pass should focus on:

- cleaner spatial layout;
- correct Workflow Task scheduling semantics;
- clearer Task movement;
- better workload triggering;
- reliable time controls.

Do **not** add cache, memory, glow, charts, or visual polish in this pass.

---

## 1. Fix Workflow Task scheduling semantics first

A Workflow Execution should never fan an Activity completion into multiple simultaneous Workflow Tasks.

Implement this rule:

```text
If new Workflow-relevant events arrive
AND there is no Workflow Task already queued or running:
    schedule one Workflow Task

If a Workflow Task is already queued or running:
    accumulate the new events for that Workflow
    do not create another simultaneous Workflow Task
```

Multiple Activity completions may therefore be handled by one subsequent Workflow Task.

Keep the opposite direction valid:

```text
one Workflow Task
→ may schedule one or many Activities
```

Acceptance:

```text
Activity A completes ─┐
Activity B completes ─┼→ one pending Workflow Task
Activity C completes ─┘
```

not:

```text
Activity completion → WFT WFT WFT
```

## 3. Keep the Temporal Service Core compact

The Temporal Service Core belongs inside the Temporal Service boundary.

It should contain or visually represent:

```text
active Workflow Executions
Workflow state
History
Task scheduling
```

Do not make it half the screen.

It should feel like a processing/state node feeding the two Task lanes.

Persistent Workflow circles belong visually near or inside this Core.

## 4. Align each Queue → Poller → Slot path horizontally

Workflow row:

```text
Workflow Task Queue → Workflow Pollers → Workflow Slots
```

Activity row:

```text

```

These components should share approximately the same Y coordinate.

A Task moving toward execution should therefore travel almost entirely left-to-right.

Avoid diagonal routing where possible.

The current perimeter route is too visually dominant.

                │

## 6. Keep Tasks and completion signals visually distinct

Maintain the semantic grammar:

```text
Workflow Execution / Workflow Start = circle ○

Workflow Task = blue square ■

Activity Task = orange square ■

Completion / command signal = neutral diamond or pulse ◇
```

A completed Task square must not fly back toward Temporal.

Instead:

```text
[■] executes
↓
Task completes/disappears

◇ completion signal
← travels to Temporal Core
```

This distinction is important.

## 8. Preserve Slot reservation semantics

Do not let Pollers fetch arbitrary excess Tasks.

Mechanically:

```text
available execution capacity
→ permits polling
→ Poller receives Task
→ Task dispatches into reserved Slot
```

The animation may look like the Poller chooses and shoots the Task into the Slot, but the Slot should already be reserved by the engine.

## 9. Replace Manual / Continuous with Triggered / Continuous

Use only two workload-generation modes:

```text
[ Triggered ] [ Continuous ]
```

### Triggered mode

UI:

```text
Workflows to start: [ 1 ]

[ Start 1 Workflow ]
```

Requirements:

- integer value;
- default `1`;
- user may set N;
- clicking the button starts exactly N Workflows;
- changing N alone starts nothing.

This subsumes both one-at-a-time and Trigger-N behavior.

Default simulator mode should be:

```text
Triggered
N = 1
```

This is the teaching mode.

### Continuous mode

UI:

```text
Rate: [ 6 ] [ per minute ▼ ]
```

Support:

```text
per second
per minute
per hour
```

Normalize internally.

Suggested default:

```text
6 / minute
```

not 12/minute.

Continuous mode is for load/capacity experiments.

## 10. Make time scale one authoritative state value

Fix the observed bug where `8x` remained effectively active after moving the slider back to `1x`.

There must be exactly one authoritative:

```text
timeScale
```

All controls modify that same value.

Examples:

```text
slider → setTimeScale(...)
1x button → setTimeScale(1)
4x button → setTimeScale(4)
8x button → setTimeScale(8)
```

No separate stale:

```text
fastForwardScale
overrideScale
buttonScale
```

unless fast-forward is explicitly implemented as a momentary mode.

Acceptance sequence:

```text
1x
→ 8x
→ slider to 0.5x
→ 1x
→ 4x
→ slider to 0.25x
```

Every change must take effect on the next simulation tick and the UI must always reflect the actual engine value.

## 14. Do not imply that Temporal executes Workflow code

The Worker executes Workflow Tasks.

The Workflow Slot is where Workflow code produces commands such as:

```text
schedule Activity
complete Workflow
start Timer
```

Then a completion/command signal returns to the Temporal Core.

The Core records/applies state and schedules subsequent Tasks.

Do not visually imply that the Core independently decides what application logic should run.
