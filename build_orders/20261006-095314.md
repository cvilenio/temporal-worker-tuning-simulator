# Temporal Worker Scaling Simulator — Cache & Worker RPC Test Order

## Objective

Validate that the current Workflow Cache implementation and Worker→Temporal completion behavior are mechanically correct.

Do **not** change the visual design unless a test exposes a rendering inconsistency.

Run tests in this order:

1. engine semantics
2. cache correctness
3. replay correctness
4. Worker RPC / completion semantics
5. renderer synchronization
6. manual visual scenarios

If an earlier layer fails, fix it before continuing.

---

## 1. Cache insertion test

Configuration:

```text
1 Worker
Workflow Cache Capacity = 4
Triggered mode
Start 1 Workflow
Activities / Workflow > 0
```

Expected sequence:

```text
initial Workflow Task runs
→ Workflow remains open
→ Workflow inserted into cache
```

Assertions:

- cache contains the Workflow after the initial WFT completes;
- cache entry references the correct Worker;
- cache size becomes `1`;
- `cachedWorkerId` is set;
- no Activity Task causes cache insertion directly.

Pass condition:

```text
Workflow cache insertion occurs only after successful Workflow Task execution.
```

---

## 2. Cache hit test

Continue the same Workflow until another Workflow Task is scheduled.

Expected:

```text
next WFT reaches same Worker
→ cache entry exists
→ CACHE_HIT
→ no replay phase
→ normal Workflow execution
```

Assertions:

```text
cacheHit = true
replayCpu = 0
```

and:

- cache entry `lastUsedAt` is refreshed;
- Workflow Slot never enters `RUNNING_REPLAY`;
- cache-hit counter increments exactly once.

---

## 3. Cache miss test

Setup:

```text
Cache Capacity = 1
```

Create enough Workflows to evict an earlier Workflow.

Then allow that evicted Workflow to receive another Workflow Task.

Expected:

```text
WFT arrives
→ cache entry absent
→ CACHE_MISS
→ replay
→ normal Workflow execution
```

Assertions:

```text
cacheHit = false
replayCpu > 0
```

and:

- `REPLAY_STARTED` emitted;
- `REPLAY_COMPLETED` emitted;
- cache-miss counter increments once.

---

## 4. LRU eviction test

Use deterministic engine-level testing.

Configuration:

```text
Cache Capacity = 2
```

Sequence:

```text
W1 WFT completes
W2 WFT completes

cache:
W1, W2

W1 receives another WFT
→ cache hit
→ refresh W1 recency

W3 WFT completes
```

Expected:

```text
W2 evicted
```

Final cache:

```text
W1
W3
```

Assertions:

- exactly one eviction occurs;
- evicted Workflow is `W2`;
- `W1` survives because it was most recently used;
- no random or FIFO eviction behavior.

This test is especially important.

---

## 5. Replay-and-rewarm test

Sequence:

```text
W1 cached
→ W1 evicted
→ later W1 gets WFT
```

Expected:

```text
CACHE_MISS
→ replay
→ Workflow Task executes
→ W1 inserted back into cache
```

Assertions:

- replay occurs exactly once;
- W1 becomes warm again after successful WFT execution;
- `cachedWorkerId` is restored;
- cache entry gets a fresh LRU timestamp.

---

## 6. Workflow completion cache-cleanup test

Setup:

```text
W1 currently cached
```

Run its final Workflow Task.

Expected:

```text
final WFT executes
→ completion commands returned
→ Workflow becomes COMPLETED
→ W1 cache entry removed
```

Assertions:

- completed Workflow has no cache entry;
- `cachedWorkerId = null`;
- cache size decreases;
- green completion/check UI may remain temporarily, but engine cache state must already be cleared.

---

## 7. Cache Capacity = 0 test

Configuration:

```text
Workflow Cache Capacity = 0
```

Expected:

- no Workflow remains cached;
- initial WFT may execute normally;
- every subsequent WFT requiring prior state is a cache miss;
- replay occurs every time;
- cache size remains `0`.

Assertions:

```text
cacheSize === 0
```

at all times after each tick settles.

No hidden cache entries.

---

## 8. Live cache resize downward test

Start with:

```text
Cache Capacity = 5
```

Fill cache with:

```text
W1 W2 W3 W4 W5
```

Change:

```text
5 → 2
```

Expected:

- LRU eviction occurs immediately;
- exactly 3 entries removed;
- the two most recently used remain.

Assertions:

```text
cacheSize <= 2
```

after the config update finishes.

No random removals.

---

## 9. Live cache resize upward test

Start:

```text
Capacity = 2
```

Cause some Workflows to be evicted.

Then increase:

```text
2 → 10
```

Expected:

- existing warm entries remain;
- evicted Workflows do **not** magically reappear;
- future successful WFTs may warm them again.

This verifies that cache capacity is not being confused with durable Workflow state.

---

## 10. Replay must not rerun Activities

This is a hard semantic test.

Create a Workflow with completed Activities, evict it, then force a replay.

Expected:

```text
Workflow replay
```

must not create:

- new Activity Tasks;
- new Activity Slot occupancy;
- duplicate Activity completions.

Assertions:

```text
activityTaskCount unchanged due solely to replay
```

and:

```text
activityCompletionCount unchanged
```

Replay only reconstructs Workflow state.

---

## 11. Replay cost scales with History

Create two otherwise similar Workflows:

```text
W1: small History
W2: larger History
```

Evict both and force replay.

Expected:

```text
replayCpu(W2) > replayCpu(W1)
```

assuming the current model uses history-size-proportional replay work.

This verifies that replay is not just a fixed cosmetic delay.

---

## 12. Replay uses shared CPU

Set:

```text
low Worker CPU
multiple replaying Workflow Tasks
```

Expected:

- replay raises shared CPU utilization;
- Workflow Tasks remain in Slots longer;
- Activity CPU work, if present, competes for the same CPU;
- replay duration increases under contention.

This is important for the educational model.

---

# Worker / Temporal RPC semantics

## 13. Workflow Task completion test

When a Workflow Task finishes execution, verify:

```text
Worker
→ RespondWorkflowTaskCompleted-equivalent event
→ Temporal Core
```

The visual return object may be a diamond/pulse, but engine semantics should represent:

```text
commands/results sent Worker → Temporal
```

Expected:

- Task does not fly back into its queue;
- completion/commands are processed by the Core;
- any resulting Activity Task is created only after Core processing.

---

## 14. Activity Task completion test

When an Activity finishes:

Expected semantic sequence:

```text
Activity Slot
→ Worker reports Activity completion
→ Temporal Core records result
→ Workflow becomes eligible for next WFT
```

Assertions:

- completed Activity Task itself does not return to queue;
- exactly one completion/result event goes Worker→Temporal;
- subsequent Workflow Task is created by the Core, not by the Activity Slot directly.

---

## 15. No inbound Worker push assumption

Verify the engine does not model:

```text
Temporal proactively pushes Task into idle Worker
```

without an eligible Poller.

Required test:

```text
Pollers = 0
Slots > 0
queued Tasks > 0
```

Expected:

```text
nothing leaves the queue
```

This should remain true even with a warm cache.

Cache affinity must never bypass polling.

---

# Renderer synchronization

## 16. Cache-state visual consistency

At every frame:

```text
visible cache entry [W1]
```

must correspond to an actual engine cache entry.

No stale visual cell after eviction or Workflow completion.

No visual cache hit highlight if engine reported a miss.

---

## 17. Replay-state visual consistency

A Workflow Slot may show:

```text
REPLAY
```

only when:

```text
task.state === RUNNING_REPLAY
```

Once engine transitions to normal Workflow decision execution, remove the Replay indicator.

No independent timer should make the UI replay longer or shorter than engine state.

---

## 18. Cache hit visual consistency

A cache cell may highlight as a hit only when an actual:

```text
CACHE_HIT
```

event occurred for that Workflow and Worker.

No heuristic such as:

```text
Workflow ID exists somewhere in UI
```

should trigger the highlight.

---

## 19. Cache eviction visual consistency

When engine emits:

```text
CACHE_EVICTED(W2)
```

the visible cache entry for W2 must disappear/reflow.

No placeholder gap should remain.

Reuse the same compaction principle already used for Active Workflows.

---

Set:

```text
Cache Capacity = 0
```

Run several Workflows.

Expected:

```text
every subsequent WFT
→ replay
```

Then raise:

```text
0 → 10
```

Expected:

- future WFTs begin producing cache hits;
- replay frequency drops.

If memory-pressure eviction is already implemented:

Start:

```text
high cache capacity
low memory
```

Expected:

```text

→ memory pressure

```

Expected:

```text
fewer forced evictions

→ less replay CPU
```

# Final pass criteria

Do not consider cache implementation validated until all of these are true:

- LRU behavior is deterministic.
- Cache insertion occurs after successful WFT execution.
- Hits eliminate replay.
- Misses cause replay.
- Replay consumes CPU.
- Replay cost depends on History size.
- Replay never re-executes completed Activities.
- Completed Workflows are removed from cache.
- Capacity changes behave correctly.
- Cache visuals reflect engine state exactly.
- Polling is still required even for warm Workflows.
- Worker completion traffic is modeled Worker→Temporal, not Temporal push into Worker.

If these tests pass, I’d consider the current single-Worker cache model solid enough to move on to the next major feature: **multi-Worker sticky affinity and timeout fallback**.
