## Queue admission + zero-capacity pass

Implement this as a focused correctness/interaction pass. Preserve the current topology, green Workflow completion behavior, Triggered/Continuous modes, and completion-return rail. Do not add new features or aesthetic polish. The main goals are to make queue admission visually and semantically consistent, align the Workflow Start emitter with the Active Workflows row, and allow Pollers/Slots to reach zero.

### 1. Move the Workflow Start emitter down

The Client emitter should align vertically with the first row of Active Workflow circles rather than aiming at the “Active Workflows” label and then dropping downward.

Target:

```text
CLIENT                 TEMPORAL CORE

  ○  ───────────────►  ○ ○ ○ ○
                       active workflows
```

The incoming Workflow Start circle should travel almost horizontally into the position where a newly active Workflow will appear.

Avoid:

```text
○ ─────► label/header
             ↓
             ○
```

When the request arrives, transform or hand off cleanly into the persistent Workflow Execution circle.

---

### 2. Make queue admission a real simulation state

Add an explicit distinction between:

```text
ENQUEUING
QUEUED
DISPATCHING
```

A newly scheduled Task should behave like:

```text
Temporal Core
     │
     │ Task created
     ▼
 ENQUEUING
     │
     │ travels into queue
     ▼
  QUEUED
     │
     │ now eligible for Poller
     ▼
DISPATCHING
```

While `ENQUEUING`:

- it is visibly moving from the Core into the queue;
- it does **not** count toward displayed queue depth;
- it cannot be acquired by a Poller.

Only once it reaches its assigned queue-storage position does it transition to `QUEUED`.

This makes the visual and metric state agree.

---

### 3. Right-anchor the queue contents

Use the Worker-facing side of the queue as the egress side.

So:

```text
Core                            Worker
 ↓                                ↓

┌───────────────────────────────┐
│                 ■ ■ ■ ■       │ ───► Poller
└───────────────────────────────┘
                  oldest →
```

The oldest Task should be closest to the right edge / Pollers.

When there is only one Task:

```text
┌───────────────────────────────┐
│                         ■     │
└───────────────────────────────┘
```

That means a newly created Task gets a meaningful visible journey across the queue before becoming pollable.

This is preferable to left-anchoring because:

- incoming work is easier to notice;
- the queue's exit is physically near the Pollers;
- FIFO direction is intuitive;
- there is no “Task immediately gets yanked off the left side” effect.

---

### 4. Fill additional queue positions right-to-left

For multiple queued Tasks:

```text
newest                         oldest
   ■   ■   ■   ■   ■   ■   ■
                           → Poller
```

The oldest Task occupies the rightmost position.

New Tasks join behind it, progressively filling toward the left.

Do not place Tasks arbitrarily within the queue rectangle.

Each queue should have deterministic storage positions.

---

### 5. A Task cannot be polled until it has settled

This should be a hard engine invariant:

```text
task.state === QUEUED
```

must be true before a Poller may acquire it.

A Task still moving across:

```text
Core → Queue
```

must not suddenly veer toward a Poller.

This is the behavior currently making the animation look inconsistent.

---

### 6. Give a newly queued Task a brief visible dwell

Even after it reaches its queue position, prevent it from being acquired on effectively the exact same frame.

Add a short normalized queue settle/dwell interval.

Suggested:

```text
250–400 ms at 1x
```

Conceptually:

```text
arrives at queue position
        ↓
briefly visible as queued
        ↓
becomes eligible for polling
```

This is pedagogical presentation timing, not a claim about real Temporal queue latency.

At fast-forward speeds it can become correspondingly brief.

---

### 7. Queue count semantics

Displayed queue depth should mean:

> Tasks that have actually reached the queue and are waiting there.

Therefore:

```text
ENQUEUING   → not counted
QUEUED      → counted
DISPATCHING → no longer counted
```

This gives a very clean correspondence between:

```text
number shown in queue metric
```

and:

```text
number of Task objects visibly waiting in the queue
```

If visible Task rendering is later aggregated because of very large backlogs, the numeric count remains authoritative.

---

### 8. Keep FIFO polling from the right edge

Pollers should always acquire the oldest eligible Task from the queue's right/egress side.

Example:

```text
Queue

■ ■ ■ ■ ■
        ↑
        next Task

         · · · · → ○ Poller
```

When it leaves, remaining Tasks may shift right to compact the line.

---

### 9. Queue compaction

When the oldest Task leaves:

Before:

```text
■ ■ ■ ■
      ↑ leaves
```

After:

```text
  ■ ■ ■
```

or smoothly:

```text
■ ■ ■ → shift toward right
```

Do not preserve invisible holes.

This is the same principle used for the Active Workflow circles.

---

## 10. Allow Poller count to reach zero

Change both controls to allow:

```text
0 Workflow Pollers
0 Activity Pollers
```

This is pedagogically useful even if it represents an intentionally broken Worker configuration.

Expected behavior at `Pollers = 0`:

```text
Task Queue:
■ ■ ■ ■ ■ ■

Pollers:
(none)

Slots:
[ ][ ][ ][ ]

CPU:
0%
```

Backlog should grow naturally.

No Tasks may leave the queue.

---

## 11. Allow Slot count to reach zero

Likewise allow:

```text
0 Workflow Slots
0 Activity Slots
```

Expected behavior with Pollers > 0 but Slots = 0:

```text
Queue:
■ ■ ■ ■ ■

Pollers:
○ ○ ○

Slots:
(none)
```

Because there is no execution capacity, Pollers should not acquire Tasks.

Remember the engine rule:

```text
polling eligibility requires execution capacity
```

So zero Slots means zero Tasks leave the queue, regardless of Poller count.

---

### 12. Live transition to zero must drain safely

If the user changes:

```text
Activity Slots: 4 → 0
```

while 4 Tasks are already running:

- all four existing Tasks continue;
- they complete normally;
- those Slots retire afterward;
- no new Activity Tasks are acquired;
- final stable Slot count becomes zero.

Do not terminate running work.

Likewise, setting Pollers to zero:

- currently dispatching Pollers finish their current dispatch;
- they then retire;
- no additional Tasks are acquired.

---

## 13. Add explicit zero-capacity learning tests

These should become useful demo configurations.

### No Pollers

```text
Pollers = 0
Slots = 8

Result:
queue grows
Slots remain empty
```

Lesson:

> Execution capacity is useless if the Worker is not retrieving work.

### No Slots

```text
Pollers = 8
Slots = 0

Result:
queue grows
Pollers cannot retrieve work
```

Lesson:

> Polling capacity is useless without execution capacity.

### Restore capacity

While backlog exists:

```text
Pollers 0 → 2
```

or:

```text
Slots 0 → 4
```

The user should visibly see work begin flowing again.

These will actually be excellent teaching scenarios.

---

## 14. Preserve the current lane geometry

Don't redesign the topology.

Keep:

```text
Core → Queue → Poller → Slot
```

as the horizontal work direction.

Keep the middle completion-return lane.

The queue fix should make that horizontal grammar much cleaner.

---

## Acceptance test

Use:

```text
Triggered mode
Start 1 Workflow
1x
```

Watch the initial Workflow Task.

It must visibly do this:

```text
Core creates blue ■

■ ─────────────────────►

┌──────────────────────────────┐
│                         ■    │
└──────────────────────────────┘
                         ↑
                   now QUEUED

brief dwell

                         ■ ───► ○ Poller ───► [■]
```

It must **not** do:

```text
Core ■ ───────────╲
                  ╲
                   ○ Poller
```

before reaching its queue position.

Then repeat for Activity Tasks.

---

I think **right-anchored queues are the best choice** here. They reinforce that the queue is the staging area immediately before Worker acquisition, and they force every Task to have a visible, consistent moment of “I am now actually waiting in this queue” before a Poller can touch it.

And allowing `0` for Pollers and Slots is a very good addition. It makes the simulator better pedagogically because you can demonstrate each capacity mechanism by completely removing it rather than only showing degrees of insufficiency.
