## Next pass — active Workflow compaction, full Worker controls, queue anchoring

### 1. Compact the Active Workflows area after completion

The Active Workflows display must contain **only currently active Workflow Executions**.

When a Workflow enters its completed/checkmark state:

```text
ACTIVE
→ COMPLETED_HOLD
→ fade out
→ remove from active visual layout
```

After removal, recompute the positions of all remaining active Workflow circles.

Do not preserve the completed Workflow’s old layout index.

Bad behavior:

```text
○   [empty]   [empty]   ○   ○
```

Desired behavior:

```text
○  ○  ○
```

If another Workflow starts:

```text
○  ○  ○  ○
```

not:

```text
○  [old empty positions]  ○
```

Implementation requirement: visual positions should be derived from the **current filtered collection of visible Workflow Executions**, not from permanent Workflow sequence IDs or original array indexes.

Stable Workflow IDs should remain stable; only their screen position may reflow.

A small smooth reflow animation is fine, but correctness comes first.

---

### 2. Do not count completed-hold Workflows as permanent active slots

The green-check behavior is working well, so keep it.

While a Workflow is in its ~2-second completion hold, it can remain in the Active Workflows row.

Once its hold/fade completes, it must be removed from the layout completely and remaining circles compact immediately.

So:

```text
○  ○  ✓  ○

~2 seconds later

○  ○  ○
```

### 3. Add Workflow Poller and Workflow Slot controls

The current Worker controls expose:

- Activity Pollers
- Activity Slots
- CPU

Add:

- **Workflow Pollers**
- **Workflow Slots**

So the Worker controls should now include:

```text
Workflow Pollers   [slider] N
Workflow Slots     [slider] N

Activity Pollers   [slider] N
Activity Slots     [slider] N

CPU capacity       [slider] N
```

These must be independent values.

Do not tie Workflow capacity to Activity capacity.

Suggested initial ranges:

```text
Workflow Pollers: 1–10
Workflow Slots:   1–16

Activity Pollers: 1–10
Activity Slots:   1–32
```

Use the same live-change semantics already defined for Activity capacity.

---

### 4. Verify Workflow Poller/Slot changes affect engine behavior, not just rendering

This must not be a UI-only addition.

Changing Workflow Pollers should affect Workflow Task retrieval throughput.

Changing Workflow Slots should affect Workflow Task execution concurrency.

Required test:

```text
Workflow backlog = several Tasks
Workflow Pollers = 1
Workflow Slots = 4
```

Only one Workflow Poller may be in an acquisition/dispatch cycle at once.

Increase:

```text
Workflow Pollers → 2
```

and two Pollers may concurrently retrieve work, subject to available Workflow Slots.

---

### 5. Give each Task Queue explicit ingress, storage, and egress anchors

The current animation sometimes makes a queued square appear on the left side of the box and sometimes on the right, which makes the queue feel spatially inconsistent.

Define explicit geometry for every queue:

```text
queueIngress
queueStoragePositions[]
queueEgress
```

All must share the lane's exact Y coordinate.

Conceptually:

```text
Core
  │
  ▼

INGRESS                         EGRESS
  ↓                               ↓
  ■  ■  ■  ■  ■  ■  ■  ■  ■      →
┌────────────────────────────────────┐
│                                    │
└────────────────────────────────────┘
```

Do not allow individual animation states to invent their own Queue coordinates.

---

### 6. Use one consistent queue-packing rule

I recommend packing queued Tasks **from the egress side backward**.

The oldest Task should be closest to the Worker.

Example:

```text
newer                    oldest
  ■   ■   ■   ■   ■   ■
                      → Poller
```

When a Task leaves:

```text
■ ■ ■ ■ ■
```

remaining Tasks may slide toward the egress position.

This visually reinforces FIFO behavior.

If that reflow proves distracting, a simpler fixed-cell queue is acceptable, but every Task still needs to occupy an explicit queue cell.

Do not show arbitrary positions inside the queue.

---

### 7. Distinguish enqueue transit from queued state

The likely source of the visual inconsistency is that you're seeing different Task phases.

Make them explicit:

```text
CORE_TO_QUEUE
QUEUED
QUEUE_TO_POLLER
POLLER_TO_SLOT
RUNNING
```

A Task in `CORE_TO_QUEUE` travels toward the queue's ingress point.

Once it reaches the queue:

```text
state = QUEUED
```

and it snaps/eases into its assigned queue-storage position.

Only after the engine transitions it to:

```text
QUEUE_TO_POLLER
```

may it leave that storage position toward the selected Poller.

This should prevent the impression that a Task enters on one side on one cycle and another side on another.

---

### 8. Keep all queue Tasks on the exact lane centerline

For both Workflow and Activity queues:

```text
task.y = laneCenterY
```

for:

- entry;
- queued storage;
- exit.

No vertical offset based on queue type or Task count.

The only diagonal motion should remain local inside the Worker when a Poller dispatches to a Slot above/below the lane center.

---

### 9. Don't let a rapidly polled Task skip its visible queued state

This may be part of what you're noticing.

When Pollers are idle and capacity exists, a newly scheduled Task may logically get picked up nearly immediately. But pedagogically, it still needs to visibly register in the queue.

Add a **minimum visual queue dwell**, separate from engine timing.

For example:

```text
MIN_VISIBLE_QUEUE_DWELL = 250–400 ms real time
```

This does **not** imply real Temporal queue latency.

It is presentation-only.

The engine may already consider the Task dispatchable, but the renderer should still show:

```text
Core → Queue
       [brief visible arrival]
       → Poller
```

rather than visually cutting the corner.

At fast-forward speeds, this can be shortened or skipped.

## Acceptance tests

**Active Workflow compaction:** trigger 3 Workflows, wait for the first two to complete and fade. The remaining Workflow circles must shift together with no invisible gaps. Trigger 3 more; new circles append directly after existing visible ones.

**Queue consistency:** run at slow speed and watch ten Workflow Tasks and ten Activity Tasks enter their queues. Every Task must enter through the same ingress point, settle on the exact lane centerline, occupy a defined queue position, and exit toward the Poller from the same egress side.

**Immediate polling:** configure an empty queue, idle Pollers, and available Slots, then create one Task. Even though it can be dispatched immediately, the Task should visibly reach the queue before moving to the Poller.

**Workflow capacity controls:** create enough load to back up Workflow Tasks. Alter Workflow Pollers independently of Workflow Slots and verify each produces the correct distinct effect.

I’d do exactly this pass before adding another concept. The active-circle issue is a straightforward layout bug, but the queue-position issue matters more than it seems: once we start deliberately creating backlogs to demonstrate scaling, the queue needs to feel like a stable spatial object rather than just a rectangular region that Tasks flash through.
