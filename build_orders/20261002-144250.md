### Poller behavior is currently visually wrong

Around the Activity dispatch, there are **4 Activity Tasks queued, 2 Activity Pollers, and 2 Activity Slots**, yet all four orange squares appear to leave the queue together toward the Pollers.

That should not happen.

With:

```text
Queue depth = 4
Pollers = 2
Available Slots = 2
```

the first dispatch wave should be:

```text
Queue

■ ■ ■ ■

      two eligible tasks only
             ↓

■ ■          ○     ○
             │     │
             ▼     ▼
            [■]   [■]
```

The other two should remain visibly sitting in the queue:

```text
Queue

■ ■
```

Then, once a Poller has finished dispatching and execution capacity becomes available again, it can acquire another Task.

More generally, the number of Tasks that may leave the queue concurrently should be bounded by something like:

```text
dispatchable =
min(
    queuedTasks,
    availablePollers,
    availableOrReservedSlotCapacity
)
```

And each Poller should have **at most one Task in its acquisition/dispatch cycle at a time**.

If there are 2 Pollers but 8 empty Slots, the Worker can eventually fill all 8, but it should look like repeated waves:

```text
■ ■ → Pollers → Slots
■ ■ → Pollers → Slots
■ ■ → Pollers → Slots
...
```

not:

```text
■ ■ ■ ■ ■ ■ ■ ■ → two Pollers simultaneously
```

That distinction is exactly what lets the simulation teach why increasing Pollers changes intake rate.

I’d tell the agent to check both the **engine state and the renderer** here. In your video the queue count stays at 4 briefly while all four dots visually leave it, then drops to 2 later. That suggests there may be a mismatch between semantic dispatch state and visual interpolation, rather than only an engine bug. The hard invariant should be:

> A Task must remain visibly in the queue until that specific Task has actually transitioned to `DISPATCHING` and owns a Poller + reserved Slot.

## On the completion-return design

I would keep this design.

What works now:

```text
Workflow / Activity Slot
          │
          ◇
          ▼
═══════════════════◄ Temporal Core
```

is substantially clearer because:

- the Task square finishes at the Slot;
- a different neutral symbol represents the result;
- return traffic has one predictable lane;
- it doesn't cross the Queue→Poller→Slot path;
- the huge outer plumbing is gone.

I would make only **small presentation refinements**, not restructure it again.

First, the moving diamond currently gets a tiny `completion` label, and it collides visually with the permanent `COMMAND / COMPLETION RETURN` label in some frames. I’d remove the moving text. The diamond itself plus a legend is enough:

```text
◇ = command / completion
```

Second, I’d make the permanent dotted rail a little fainter. It should provide orientation but not compete with the Task lanes. Something like 20–30% opacity when idle, strengthening briefly while a return event is actually moving.

Third, make sure the return rail visibly terminates **at the Temporal Service Core**, not merely at the left side of the lane. The causal read should be unmistakable:

```text
Slot → ◇ → Core
              ↓
        schedules next Task
```

### So my next order to the agent would be narrowly scoped

> **Do not change the overall layout or return-lane topology. Fix dispatch correctness first.**
>
> 1. Enforce one in-flight acquired Task per Poller.
> 2. Require a reserved/available appropriate Slot before a Task leaves its queue.
> 3. Limit concurrent queue exits to `min(queue depth, available pollers, available slot capacity)`.
> 4. Keep non-dispatched Tasks visibly stationary inside the queue.
> 5. Verify renderer state follows the engine Task state exactly; no Task should start a Queue→Poller animation until that Task is actually `DISPATCHING`.
> 6. Add a test with 4 queued Activities, 2 Pollers, 2 Slots: exactly 2 may leave the queue in the first wave, and exactly 2 must remain.
> 7. Keep the current middle completion-return rail.
> 8. Remove the floating `completion` text on each return diamond and make the idle rail more visually subdued.
> 9. Confirm the diamond terminates at the Service Core before the next Task is created.
