I think your sketches are converging on the right issue, but I’d use a **third hybrid layout** rather than A or B exactly.

The key is to make **Workflow and Activity each have their own horizontal lane**, while giving return traffic a separate route so it never fights with Task movement.

### Recommended layout

```text
CLIENT        TEMPORAL SERVICE                              WORKER
              ┌──────────────────────────────┐   ┌───────────────────────────────┐
              │                              │   │                               │
   ○ ───────► │   TEMPORAL SERVICE CORE     │   │                               │
              │   Workflow state / history  │   │                               │
              │   ○ ○ ○ active workflows    │   │                               │
              │                              │   │                               │
              │           WORKFLOW LANE      │   │                               │
              │         ┌─────────────┐      │   │  ○ ○  ───────► [■][ ][ ]     │
              │   ■ ───►│ WFT QUEUE   │──────┼───┼► pollers       slots          │
              │         └─────────────┘      │   │                               │
              │                              │   │                               │
              │           ACTIVITY LANE      │   │                               │
              │         ┌─────────────┐      │   │  ○ ○  ───────► [■][■][ ]     │
              │   ■ ───►│ ACT QUEUE   │──────┼───┼► pollers       slots          │
              │         └─────────────┘      │   │                               │
              └──────────────────────────────┘   └───────────────────────────────┘

                        ◄──────── completion / command return rail ───────────────
```

So the normal direction is extremely consistent:

**Core → Queue → Poller → Slot**

Everything representing *work to be executed* moves left-to-right.

The only thing moving right-to-left is a visually distinct **completion/command/event signal**, using a dedicated return rail rather than retracing the Task path.

That gives us two very clean rules:

```text
TASKS       ■  ─────────────────────────────►
RESULTS     ◇  ◄─────────────────────────────
```

I think that will be much easier to understand than either diagonal return traffic or a Core floating above everything.

### Why I prefer this over A

A gets the horizontal alignment right, but the Core sitting above the queues means the return path from Slots → Core wants to diagonally cross the outgoing lanes.

### Why I prefer this over B

B has nice spatial economy, but it risks making the Worker look like it's **inside Temporal** unless the outer boundary is just an unlabeled canvas. We’ve worked pretty hard to establish the correct ownership boundaries, so I wouldn’t muddy that now.

The hybrid keeps:

```text
Temporal Service
  ├─ Service Core
  ├─ Workflow Task Queue
  └─ Activity Task Queue

Worker
  ├─ Workflow Pollers + Slots
  └─ Activity Pollers + Slots
```

while still giving us almost perfectly horizontal Task motion.

## I would also change the workload modes as you suggest

I don't think we actually need **three** modes.

Instead, collapse “manual” and “trigger N” into one generalized mode:

```text
Workflow Generation

[ Triggered ] [ Continuous ]
```

### Triggered

```text
Workflows to start:  [ 1 ]
                     [-][+]

[ Start 1 Workflow ]
```

If you change it to 10:

```text
Workflows to start:  10

[ Start 10 Workflows ]
```

This subsumes:

- one-at-a-time;
- trigger 5;
- trigger 100;
- controlled burst testing.

Default `N = 1`, so it's still perfect for teaching.

I’d probably call this **Triggered**, rather than Manual, because it describes the behavior better.

### Continuous

```text
Rate: [ 6 ] [ per minute ▼ ]

[ Start continuous load ]
```

or if continuous generation automatically runs whenever selected, simply show the rate.

So conceptually:

```text
Triggered
= send a known batch right now

Continuous
= continually create Workflows at a rate
```

That is simpler and more powerful than:

```text
Manual
Trigger N
Continuous
```

# Brief I would give the agent

## Layout restructuring

Rework the primary scene into **two horizontal execution lanes**.

### Workflow lane

```text
Temporal Core
    ↓ creates WFT

Workflow Task Queue
    ↓

Workflow Poller
    ↓

Workflow Slot
```

All movement after Task creation should primarily be horizontal left-to-right.

### Activity lane

```text
Temporal Core
    ↓ creates Activity Task

Activity Task Queue
    ↓

Activity Poller
    ↓

Activity Slot
```

Again, left-to-right.

Workflow Pollers and Workflow Slots must be horizontally aligned with the Workflow Task Queue.

Activity Pollers and Activity Slots must be horizontally aligned with the Activity Task Queue.

---

## Boundary structure

Temporal Service boundary contains:

- Temporal Service Core
- Workflow Executions
- Workflow Task Queue
- Activity Task Queue

Worker boundary contains:

- Workflow Pollers
- Workflow Slots
- Activity Pollers
- Activity Slots
- later: cache / CPU / memory

Do not place the Worker inside the Temporal Service boundary.

---

## Completion / command return path

Do not send completed Task squares back toward Temporal.

After Task execution:

```text
[■] → Task disappears/completes
```

and create a separate neutral completion/command signal:

```text
◇
```

That signal should leave the Worker and travel on a **dedicated return path** back to the Temporal Service Core.

Suggested route:

- exit upward or downward from the Worker;
- enter a shared horizontal return rail;
- travel right-to-left;
- enter the Service Core.

This prevents return traffic from visually colliding with Queue → Poller → Slot traffic.

Example:

```text
                         Worker
                     ┌───────────┐
Task lane ──────────►│ ○ → [■]  │
                     │       │   │
                     └───────┼───┘
                             │
                             ◇
                             │
Return rail ◄────────────────┘
      │
      ▼
Temporal Core
```

Use this same return rail for:

- Workflow Task completion/commands
- Activity completion

The Core then creates whatever subsequent Task is appropriate.

---

## Connection lines

Keep the temporary Queue → Poller and Poller → Slot paths.

Because everything is now aligned, these should be nearly straight:

```text
Queue ■ ─────► ○ Poller ─────► [■]
```

They should appear only while a Task is actively being moved.

Do not draw permanent connections for every Poller.

---

## Workflow generation controls

Replace separate Manual / Trigger-N concepts with:

```text
Generation mode:

[ Triggered ] [ Continuous ]
```

### Triggered mode

Controls:

```text
Workflow count [ 1 ]

[ Start 1 Workflow ]
```

Requirements:

- integer count;
- default `1`;
- reasonable range such as `1–1000`;
- clicking Start emits exactly N Workflow starts immediately;
- changing N does not automatically emit anything.

This supports both lifecycle teaching and controlled burst tests.

### Continuous mode

Controls:

```text
Rate [ 6 ] [ per minute ▼ ]
```

Supported units:

```text
per second
per minute
per hour
```

Existing continuous behavior remains.

## Suggested default startup state

I’d now actually default the whole simulator to:

```text
Mode: Triggered
Count: 1
Time scale: 1x
```

rather than Continuous.

That means the first thing a new user sees is a quiet system and a button:

**Start 1 Workflow**

They click it and can watch the entire causal chain.

When they’re ready to learn scaling, they switch to:

**Continuous**

and start creating pressure.

That gives the simulator a much clearer learning progression:

```text
1. Understand one Workflow.
2. Trigger several Workflows.
3. Turn on continuous traffic.
4. Create backlog.
5. Tune Pollers / Slots / CPU / memory.
```
