## Second-pass implementation brief

### Goal

Do not add visual polish yet.

This pass should make the **causal movement of work easy to follow by eye**, even at normal playback speed.

The user should be able to visually answer:

- What did the Client emit?
- When did a Workflow Execution come into existence?
- Which objects are Tasks versus Workflows?
- Which queue is a Task waiting in?
- Which Poller claimed it?
- Which Slot received it?
- When did an Activity completion cause another Workflow Task?

---

### 1. Replace the speed dropdown with continuous control

The current `0.5x` minimum is still too fast for inspection.

Use:

```text
Speed [ slider ] [ numeric value ]
```

Suggested range:

```text
0.05× – 2×
```

with useful snap/preset points around:

```text
0.1×
0.25×
0.5×
1×
2×
```

Allow direct numeric entry if practical.

Keep a separate fast option for clearing/draining a backlog, for example:

```text
4×
8×
```

either as buttons or as the upper end of an “advanced” range.

Default speed should probably become:

```text
0.25× or 0.5×
```

### Important

Do not rely solely on global simulation speed to make movement readable.

Transit animations should have a **minimum real-time display duration**.

For example:

```text
Queue → Poller      ~350–500 ms
brief Poller claim  ~200–300 ms
Poller → Slot       ~350–500 ms
```

At high simulation speed, animation may be visually sampled or abbreviated.

At normal/slow speeds, the entire path should be unmistakable.

---

### 2. Turn the Client into an emitter

The Client should no longer just be a static circle plus:

```text
1.0 starts/sec
```

At the configured Workflow Start Rate, it should visibly emit a Workflow Start object.

Use a **circle** for Workflow-level objects:

```text
○
```

The request should travel:

```text
Client
  ○ ─────────→ Temporal
```

The rate label can remain, but it becomes explanatory rather than the only representation of traffic.

---

### 3. Establish a hard shape grammar

Use shape, not just color, to distinguish Workflows from Tasks.

#### Workflow / Workflow Start / Workflow Execution

Circle:

```text
○
```

#### Tasks

Square:

```text
■
```

Then use color to distinguish Task type:

```text
Workflow Task = blue square
Activity Task = orange square
```

So the vocabulary becomes:

```text
○ = Workflow-level object
■ = Task-level object

blue ■   = Workflow Task
orange ■ = Activity Task
```

This should remain invariant throughout the simulator.

---

### 4. Fix Workflow Execution semantics

The current Workflow Execution circle appears briefly and reads like a flashing indicator.

Instead, when the Client request reaches Temporal:

```text
incoming request ○
        ↓
persistent Workflow Execution ○
```

The Workflow Execution should remain visible while the Workflow is open.

It may be placed in the existing:

```text
Workflow Executions
```

area.

For example:

```text
Workflow Executions

○  ○  ○
```

A Workflow should disappear only when it completes.

The persistent Workflow circle should **not itself move through Pollers or Slots**.

Tasks generated by that Workflow do.

---

### 5. Do not split the start request directly into both Task types

Change the default Workflow model.

Use a simple sequential Workflow template for now:

```text
Start
 ↓
Workflow Task 1
 ↓
Activity 1
 ↓
Workflow Task 2
 ↓
Activity 2
 ↓
Workflow Task 3
 ↓
Activity 3
 ↓
Workflow Task 4
 ↓
Complete
```

Therefore:

```text
3 Activities
→ approximately 4 Workflow Tasks
→ 3 Activity Tasks
```

This gives a more realistic educational balance than:

```text
1 WFT → four Activities in parallel → final WFT
```

and makes the back-and-forth between orchestration and Activity execution visible.

The `Activities / Workflow` slider should mean the number of sequential Activities in this default Workflow template.

Fan-out can become a separate Workflow Pattern later.

---

### 6. Make Task creation visually causal

When a Workflow Task executes and schedules an Activity:

```text
Workflow ○

Workflow Slot
[ blue ■ ]

       ↓ completes decision

Activity Task orange ■
       ↓
Activity Task Queue
```

When an Activity completes:

```text
Activity Slot
[ orange ■ ]

       ↓ completion

Temporal schedules

blue ■
       ↓
Workflow Task Queue
```

This is much better than having Tasks appear independently.

The user should visually perceive:

> Activity completion caused more Workflow work.

---

### 7. Make Queue → Poller → Slot a three-stage visual transition

Right now it reads approximately as:

```text
Queue → Slot
```

with the Task briefly swiping past a Poller.

That needs to become explicitly:

```text
QUEUE
  ■

   ↓

POLLER
  ○ ← ■

brief claim/hold

   ↓

SLOT
 [■]
```

Use three distinct visual phases:

#### Phase A — leave queue

The Task visibly exits the queue.

#### Phase B — Poller claims Task

The Task reaches the selected Poller.

The Poller should briefly highlight/pulse.

Hold long enough that the relationship is readable.

For example:

```text
200–300 ms real time
```

#### Phase C — Poller dispatches to reserved Slot

The Poller should visibly orient toward or connect to the reserved Slot.

Then the same Task square travels into that Slot.

No duplicate square should be created.

---

### 8. Reserve the Slot before Poller dispatch

Preserve the engine semantics from the existing spec:

```text
available Slot
       ↓
poll becomes eligible
       ↓
Task retrieved
       ↓
Poller dispatches Task into reserved Slot
```

Do not create a hidden Worker backlog where Pollers retrieve arbitrary Tasks and wait for Slots later.

Visually this can still look like:

```text
Poller gets Task
     ↓
shoots Task into open Slot
```

but the Slot should already have been selected/reserved.

---

### 9. Slow down the Poller interaction independently of execution

Execution time and transit time are different concepts.

A CPU Activity may execute quickly or slowly according to the engine.

But:

```text
Queue → Poller → Slot
```

needs enough **visual time** to be legible.

Do not derive that entire animation duration directly from the engine's poll-dispatch milliseconds.

The renderer may intentionally exaggerate this transition pedagogically.

This is an explanatory visualization, not a network latency visualizer.

---

### 10. Make the Poller-to-Slot relationship spatially obvious

In the current screen the Pollers and Slots are separated enough that the connection is weak.

Either move them somewhat closer or make the active Poller clearly target its selected Slot.

For example:

```text
○ Poller
 \
  \
   ■
    \
     ▼
   [   ]
```

Only render the temporary connection for the Poller actively dispatching something.

Do not add permanent lines everywhere.

---

### 11. Keep the current crude style

Do not add:

- glow
- stars
- trails
- polished sci-fi effects
- charts
- background particles

yet.

The revised screen should still look like a technical diagram.

We are validating whether the motion itself communicates Temporal correctly.

---

## Acceptance tests for this pass

I’d ask the agent to verify these manually.

### Test A — Workflow start

At `0.1x` speed:

I can watch:

```text
Client emits ○
→ ○ reaches Temporal
→ persistent Workflow ○ appears
→ blue Workflow Task ■ is created
→ ■ enters Workflow Task Queue
```

without having to infer what happened.

### Test B — Polling

With backlog present:

I can visually track one Task:

```text
queue ■
→ selected Poller ○
→ brief Poller claim
→ selected Slot [■]
```

The Task never teleports and never duplicates.

### Test C — Sequential Workflow

For:

```text
Activities / Workflow = 3
```

I can observe:

```text
blue WFT
→ orange Activity
→ blue WFT
→ orange Activity
→ blue WFT
→ orange Activity
→ blue final WFT
→ Workflow ○ disappears
```

### Test D — Task-type distinction

At a glance:

```text
circles = Workflows
squares = Tasks
blue squares = Workflow Tasks
orange squares = Activity Tasks
```

### Test E — slow inspection

I can set playback to approximately:

```text
0.1×
```

and comfortably follow individual objects.

### Test F — fast drain

I can temporarily increase playback substantially to drain an intentionally accumulated backlog without changing simulation semantics.
