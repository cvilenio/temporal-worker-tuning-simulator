## Temporal Worker Scaling Simulator — Alignment + Workflow Completion Pass

### Goal

Refine the existing animation without changing the overall topology.

This pass should focus on three things:

- exact horizontal alignment of each work lane;
- centering Poller/Slot groups as they grow;
- making Workflow completion visually obvious.

Do not add new scaling features or aesthetic polish in this pass.

---

### 1. Define fixed lane centerlines

Create one authoritative Y coordinate for each execution lane:

```ts
workflowLaneY
activityLaneY
returnLaneY
```

Every relevant visual component should derive its vertical position from these values.

For the Workflow lane, the centers of all of these must align exactly:

```text
Core Task output
Workflow Task Queue contents
Workflow Queue exit
Workflow Poller group
Workflow Slot group
```

Likewise for Activity:

```text
Core Task output
Activity Task Queue contents
Activity Queue exit
Activity Poller group
Activity Slot group
```

Target:

```text
CORE ───── ■ QUEUE ───── ○ POLLERS ───── [■] SLOTS
```

not:

```text
CORE ────╲ ■ ─────╱ ○ ───── [■]
```

There should be no visible dip as a Task enters or exits its queue.

---

### 2. Derive Task transit paths from the lane center

Do not independently position animation waypoints.

For example:

```ts
queueEntry.y = workflowLaneY
queueTask.y = workflowLaneY
queueExit.y = workflowLaneY
pollerGroupCenter.y = workflowLaneY
slotGroupCenter.y = workflowLaneY
```

The same applies to Activity.

Task movement from:

```text
Core → Queue → Poller group
```

should therefore be horizontally straight.

The only vertical/diagonal movement should be the final short movement from a Poller to a specific Slot when the Slot grid contains multiple rows.

---

### 3. Center Slot groups vertically around their lane

Slot grids must not grow downward from a fixed top edge.

Current undesirable behavior:

```text
lane ───────── [ ][ ][ ][ ]
                [ ][ ][ ][ ]
                [ ][ ][ ][ ]
```

Instead:

```text
                [ ][ ][ ][ ]
lane ───────── [ ][ ][ ][ ]
                [ ][ ][ ][ ]
```

Calculate the whole grid's height:

```ts
groupHeight =
  rowCount * slotHeight +
  (rowCount - 1) * rowGap
```

Then:

```ts
groupTop = laneCenterY - groupHeight / 2
```

Lay out Slot rows from that point.

The **center of the complete Slot group must stay aligned to the lane**, regardless of whether there are:

```text
2
4
8
16
32
```

Slots.

Apply this to both Workflow and Activity Slots.

---

### 4. Apply the same rule to Pollers

If Pollers fit on one row, keep that row centered on the lane.

If Pollers wrap to multiple rows, center the **entire Poller group** around the lane using the same principle.

Do not let increased Poller count cause the whole Poller area to drift downward.

So visually:

```text
Queue ───── Poller Group ───── Slot Group
               │                   │
          centered here       centered here
                  \             /
                    lane Y
```

---

### 5. Allow individual dispatch paths to fan locally

Once a Task reaches its selected Poller, it can move diagonally to a Slot above or below the centerline.

That is acceptable and desirable.

Example:

```text
              [ ]
             ↗
○ Poller ── ■
             ↘
              [ ]
```

But this local fan-out should happen only inside the Worker.

The longer path:

```text
Core → Queue → Poller group
```

should remain straight.

---

### 6. Preserve the existing completion-return rail

Do not redesign the return topology.

Keep:

```text
Task Slot
   ↓
completion/command ◇
   ↓
return rail
   ←
Temporal Service Core
```

The current return-lane concept should remain.

It should continue to use a visually distinct completion object rather than moving Task squares backward.

---

### 7. Enforce final Workflow Task semantics

For the simulator's current sequential Workflow model:

```text
last Activity completes
        ↓
Temporal schedules final Workflow Task
        ↓
Workflow Poller
        ↓
Workflow Slot
        ↓
Workflow code completes Workflow
        ↓
command/result returned to Service Core
        ↓
Workflow Execution becomes COMPLETED
```

A Workflow must not visually become completed directly from an Activity completion.

The final Workflow Task is the transition that completes it.

---

### 8. Add an explicit Workflow completed visual state

Persistent Workflow Executions currently use a circle:

```text
○
```

When the **final Workflow Task's completion/command signal reaches the Temporal Service Core**, change that specific Workflow's visual state.

Target:

```text
○  →  green circle with ✓
```

Possible appearance:

```text
✓
```

inside the existing Workflow circle.

Requirements:

- preserve the same position;
- do not replace it with an unrelated object elsewhere;
- use green fill and/or green outline;
- clearly show a checkmark;
- keep it visible briefly;
- then fade it away.

---

### 9. Separate engine completion from visual removal

The Workflow may become logically complete immediately in the engine.

But the UI should preserve a short completion-display state.

Recommended:

```text
Engine:
RUNNING → COMPLETED

Renderer:
ACTIVE
→ COMPLETED_HOLD
→ FADING
→ removed
```

Use approximately:

```text
1.5–2.5 real seconds
```

for the completed hold.

This should be based on **real presentation time**, not simulation time.

Therefore even at:

```text
4x
8x
```

the checkmark remains visible long enough for a human to notice.

---

### 10. Couple the checkmark to the return signal

The completion animation should read causally:

```text
Workflow Slot [■]
       ↓
completion/commands ◇
       ↓
Temporal Service Core
       ↓
Workflow ○ → ✓
```

Do not turn the Workflow green while the final Task is still executing.

Do not turn it green when the final Activity completes.

The trigger is the final Workflow Task result being processed by the Core.

---

## Acceptance tests

### A. Straight Workflow lane

Pause during Workflow Task movement.

The centers of:

```text
Core output
Workflow queue Task
Workflow Poller group
Workflow Slot group
```

should sit on one obvious horizontal line.

---

### B. Straight Activity lane

Same test for:

```text
Activity queue
Activity Poller group
Activity Slot group
```

No queue-entry dip.

---

### C. Slot centering

Test Activity Slot counts:

```text
2
4
8
16
32
```

As rows are added, the complete Slot grid should remain centered on the Activity lane.

It must not progressively migrate downward.

---

### D. Poller centering

Repeat for Poller counts large enough to wrap.

The Poller group's centroid should remain aligned with the lane.

---

### E. Local Slot fan-out

With a multi-row Slot grid, the Task may move diagonally only after reaching the Poller.

Expected:

```text
Queue ─────────► Poller
                    \
                     \→ Slot
```

not:

```text
Queue
   \
    \→ Poller
```

---

### F. Workflow completion

Trigger one Workflow.

Watch until the end.

Expected lifecycle:

```text
last Activity completes
→ final blue Workflow Task appears
→ Workflow Task Queue
→ Workflow Poller
→ Workflow Slot
→ completion/command ◇
→ Temporal Core
→ Workflow circle becomes green ✓
→ remains visible ~2 seconds
→ fades away
```

---

### G. Multiple Workflow completions

Trigger several Workflows.

Each persistent Workflow circle should independently:

- remain active until its own final Workflow Task finishes;
- receive its own completed state;
- fade independently.

---

### H. Fast-forward visibility

Run at `8x`.

Workflow execution may progress quickly, but completed Workflow checkmarks should still remain visible for roughly the same real-world display duration.

---

## Do not change in this pass

Keep unchanged:

- current Temporal Service boundary;
- current Worker boundary;
- current three-lane topology;
- current Triggered / Continuous workload modes;
- current Queue → Poller → Slot semantics;
- current middle completion-return rail;
- Task shape/color grammar.

Do not add:

- cache;
- memory;
- new Workflow patterns;
- charts;
- glow;
- space effects;
- visual polish.

The pass is complete when the diagram feels geometrically stable as Poller/Slot counts change, and a user can unmistakably see when each Workflow successfully finishes.
