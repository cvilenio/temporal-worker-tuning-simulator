## Next-pass change request

### 1. Fix Activity completion → Workflow Task behavior

Change the Temporal Service Core so that Activity completions are **coalesced** into at most one pending Workflow Task per Workflow Execution.

Conceptually:

```text
Activity A completes ─┐
Activity B completes ─┼──→ Temporal Service Core ─→ one Workflow Task ■
Activity C completes ─┘
```

not:

```text
Activity completes
      ↓
■ ■ ■ multiple Workflow Tasks
```

A useful engine rule is:

```text
if workflow has unprocessed new events
and no Workflow Task is already queued/running:
    schedule one Workflow Task
else:
    append new events to the Workflow's pending event set
```

That is much closer to the actual mental model.

The visual should reinforce:

> Multiple events can wake a Workflow, but the Workflow Task processes the accumulated new history.

I would also prevent multiple Workflow Task squares for the **same Workflow Execution** from appearing simultaneously in normal operation.

### 2. Add two workload-generation modes

I strongly agree with adding this.

Use:

```text
Workflow Starts

(●) Manual
( ) Continuous
```

#### Manual mode

Show a prominent button:

```text
[ Start Workflow ]
```

Every click emits exactly one new Workflow Start request.

This should probably become the **default teaching mode**.

It lets someone follow:

```text
one Workflow
→ WFT
→ Activity
→ WFT
→ ...
→ complete
```

without new Workflow circles continuously appearing.

It is also ideal for demos and screenshots.

#### Continuous mode

Expose:

```text
Rate: [ 6 ] [ per minute ▼ ]
```

or similar.

This is the mode for studying:

- backlog
- throughput
- scaling
- saturation
- steady state

That cleanly separates two use cases:

```text
Manual
= understand lifecycle

Continuous
= understand capacity
```

I think that's a very useful distinction for the whole product.

### 5. Yes, add Queue → Poller connectivity — but only when active

Looking at the recording, I agree something is visually missing there.

You currently have roughly:

```text
Queue       Poller ....... Slot
```

so the Poller→Slot relationship is shown, but **how the Poller acquired the Task** isn't.

I would add a temporary path:

```text
Queue ■
     \
      \ . . . .
               ○ Poller
```

during retrieval.

Then:

```text
○ Poller . . . . ■ → [ Slot ]
```

But I would **not add a permanently visible dotted line** between every queue and every Poller.

That would quickly become a spaghetti diagram, especially with multiple Workers.

Use transient connection lines only during an active operation:

```text
Workflow Queue → Workflow Poller
Activity Queue → Activity Poller
```

and color them according to Task type if useful.

So the complete lifecycle becomes:

```text
Temporal Core
     │
     ▼
Task Queue
     │  temporary claim path
     ▼
Poller
     │  temporary dispatch path
     ▼
Slot
     │
     │ completion/result path
     ▼
Temporal Core
```

That gives every leg of the cycle a visual explanation.

### 6. I would differentiate those three paths

At this point I think the path grammar should become explicit:

**Core → Queue**  
Short solid/downward movement of a Task square.

**Queue → Poller → Slot**  
Task-colored temporary dotted/dashed path.

**Slot → Core**  
Neutral completion signal, not a Task.

Something like:

```text
TASK MOVEMENT
■ · · · · → ○ · · · · → [■]

COMPLETION
[■] - - - - - - - - → ◇ Core
```

The completion object disappears at the Core.

That will help substantially when several things happen at once.

### 7. One additional correction I'd make now

The current Core label in your video says roughly:

> Workflow state · History · Task scheduling

That's good.

But the animation should also respect the distinction that **the Worker executing the Workflow Task is what generates commands**, while Temporal persists those commands/events and schedules resulting work. The docs describe the Worker running the Workflow Task, generating commands, and sending those commands back to the Service. :chatgpt-content-reference{index="2"}

So visually:

```text
Workflow Slot
   [blue ■]
       │
       │ commands
       ▼
Temporal Core
       │
       │ schedules
       ▼
Activity Queue
```

That is a better causal story than making the Service Core appear to independently decide that an Activity should happen.
